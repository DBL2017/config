# TP-LINK 代码评审 Skill

按 TP-LINK 嵌入式 Linux/C/C++ 规范进行代码评审，关注正确性、稳定性、安全性和可执行的缺陷建议。所有 C/C++ 审查均须完成资源与锁的生命周期闭环。评审代码只读，不修改代码，也不提交 Gerrit 评论或投票。

## 依赖与必须配置

- Gerrit 评审需要 Python 3.8+、HTTPS 访问及下方 HTTP 凭据；不使用 SSH。
- 本地 Git diff 或 commit 评审需要 Git。
- 完整文件和模块评审共用完整源码流程，记录工具需要 POSIX 环境和 Python 3。
- 评审 Gerrit 前，先登录 [Gerrit HTTP Credentials](https://gerrit.hn.tp-link.com/settings/#HTTPCredentials) 页面生成 HTTP Token。

使用页面显示的 HTTP 用户名和生成的 HTTP TOKEN，在启动 Copilot 的环境中设置：

```sh
export GERRIT_AUTH_NAME='你的 HTTP 用户名'
export GERRIT_AUTH_TOKEN='你的 HTTP TOKEN'
```

设置变量后再启动 Copilot；如果 Copilot 已运行，需重启以继承新环境。不要将 Token 提交到仓库或写入日志。

## 使用方式

先选择与需求匹配的评审目标。不同目标对应不同的代码基线和问题归属范围：

| 评审目标 | 检查的代码 | 问题归属 |
|---|---|---|
| 模块/子系统 | 当前实现及相关头文件、构建配置、测试和必要调用方 | 检查模块当前行为，不要求存在 diff |
| 完整文件 | 指定文件全文及必要支撑上下文；与模块共用完整源码流程 | 仅该文件为评审目标，不声称问题由某次变更引入 |
| 代码片段/选区 | 指定行范围、选区或粘贴函数及必要上下文 | 仅检查指定片段，不自动扩大到完整文件 |
| 已暂存变更 | 默认检查当前仓库的 `git diff --cached` | 只报告暂存变更引入的问题，或其显著改变可达性/行为的旧问题 |
| 粘贴的 diff/patch | 用户提供的 diff 和必要上下文 | 只检查所提供的变更范围 |
| commit/hash/ref | 指定提交相对其第一父提交的变更 | 只报告该提交引入或实质改变的问题 |
| Gerrit change/patchset | 指定 patchset 相对其第一父提交的变更 | 只报告该 patchset 引入或实质改变的问题；不会改用本地工作树或最新 patchset |

### 按目标发起评审

在请求中写明目标类型和路径、版本或范围。可参考以下示例：

```text
# 模块：评审当前模块实现，不需要先暂存变更
请按 TP-LINK 规范评审模块 src/network/wifi。
重点检查配置加载、连接状态和资源清理。

# 完整文件：与模块共用覆盖门禁和文件报告，不扩展为目录审计
请完整评审 src/net/wifi.c 当前实现，并查看必要的头文件和直接调用方。

# 选区：仅检查指定范围，结果直接在对话中给出
请评审 src/net/wifi.c:20-60，不扩大到整个文件。

# 代码片段：以粘贴内容为准，必要时补充调用契约
请评审下面的 C 函数，重点检查错误处理和缓冲区边界：
<粘贴代码>

# 当前变更：仅评审已经暂存的内容
请评审当前仓库已暂存的 TP-LINK 规范符合性和正确性问题。

# 指定 diff：仅评审所提供的补丁
请评审下面的 diff，只报告由本补丁引入或实质改变的问题：
<粘贴 diff>

# commit：与该提交的第一父提交比较
请按 TP-LINK 规范评审 commit <commit-id>。

# Gerrit：明确 change 和 patchset，避免评审错误版本
请评审 Gerrit patchset：
https://gerrit.example.com/c/team/project/+/12345/3
```

### 范围与版本注意事项

- **模块名有歧义时**，Skill 会先确认模块范围；模块评审检查当前实现及必要的集成上下文，不等同于检查 staged diff。
- **只指定文件或代码片段时**，按当前内容评审；如需判断变更归属，请提供 diff、commit 或 Gerrit patchset。
- **完整文件与模块共用流程**，但目标清单不同：完整文件仅包含该文件，模块按目录和构建输入确定实现文件。读取头文件、调用方、配置或测试只用于核实目标契约，不会自动将它们纳入全面审计或覆盖计数；明确指定某个头文件或脚本全文时，该文件本身就是目标。
- **完整 buffer 与选区分开处理**：明确要求评审整个 buffer 且可取得全文时走完整文件流程；指定行范围、选区或粘贴函数仍走代码片段流程。未保存的 buffer 不会被磁盘版本悄悄替换。
- **未指定具体目标、只要求评审当前仓库变更时**，Skill 只检查**已暂存**的 diff。未暂存修改不会自动纳入；先 `git add` 需要评审的内容，并避免把无关修改一并暂存。
- **指定 commit 或 Gerrit patchset 时**，只使用所选版本及其必要的同版本上下文。不会用工作树中的新代码补齐所选版本缺失的上下文。
- **Gerrit URL 应包含 patchset 编号**。Skill 先取得并校验精确 patchset 的 diff，只有分析确有需要时才读取对应版本的源文件。
- **没有评审目标且不存在有效 staged diff 时**，Skill 会说明无法评审，不会自行扩大范围扫描整个仓库。

完整文件和模块评审均生成 Markdown 报告文件，对话中仅交付报告路径和评审状态。
报告写入评审开始时的工作目录，命名为 `YYYY-MM-DD-Target-评审报告-v1.md`：
完整文件的 Target 为含扩展名的文件名，模块为目录名；续评更新同一报告。
代码片段、diff、staged、commit 和 Gerrit 评审保持原有对话输出，不生成报告文件。
评审说明使用简体中文，路径、符号和代码片段保留原文。

Gerrit 获取失败时不会评审不完整的产物：**401** 检查 Token 和启动环境；**403** 通常表示账号无访问权限；**404** 可能表示 change 不存在或账号不可见。Skill 会报告实际获取阶段和错误，不会回退到本地代码。

详细 Gerrit 获取说明见 [`references/gerrit-retrieval.md`](references/gerrit-retrieval.md)。

## 工作流程

Skill 按以下阶段完成评审；评审过程中只读目标代码，不修改代码或提交
Gerrit 评论。

1. **确定评审范围与代码版本**：根据输入类型选定唯一依据。模块评审检查当前
   实现；文件评审检查指定文件及必要上下文；仓库评审在未指定目标时只检查已
   暂存 diff；commit 评审比较指定提交与其第一父提交；Gerrit 评审只使用指定
   patchset。粘贴的 diff 则以用户提供内容为准。
2. **准备适用规则与上下文**：先读取通用验证规则，再按目标加载 TP-LINK C
   规则；所有 C/C++ 审查都必须加载资源生命周期闭环规则，其他参考按目标加载。
   理解接口契约、调用方、资源归属和构建条件；Gerrit 只通过 HTTPS 获取精确版本，
   失败时停止，不用本地工作树或最新分支替代。
3. **检查并验证证据**：先建立代码整体行为，再追踪关键正常/异常路径、输入和
   接口、资源生命周期及共享状态。C/C++ 必须逐项核对资源获取、所有适用出口、
   释放/转移及实际构建条件；对每个疑点确认触发条件、实际错误行为和目标版本归属，
   检查附近校验、清理与同步逻辑；按根因去重，给出最小且可执行的修复建议。
   完整文件和模块在统一初审及集成门禁中核对可变状态的完整读写区间、
   `strncpy`/`sscanf`/字符串边界、资源清理和错误返回值处理；代码片段仍在指定
   范围内完成原有内部闭环，不创建完整源码台账。工具不可用本身不等于代码缺陷。
   完整源码评审还须逐目标登记四类风险调用点：字符串边界、字段扫描、
   结构化输入、分配与文件读取。每个调用点记录具体输入/容量或结构契约、
   校验与失败处理，分别处置为安全、确认缺陷、构建/路径排除或待确认。
   当前不生效的危险分支保留排除证据；安全反例不因 API 名称而误报。
4. **按评审类型完成并交付**：
   - **代码片段、diff、staged、commit、Gerrit**：保持请求范围，按报告格式在
     对话中用简体中文给出结论、问题、原因、建议、规则分类标签及精确规则依据；
     TP-LINK 规则引用稳定 ID 和章节，项目契约单独引用代码证据。没有问题时使用
     规定的简洁通过结论，不生成评审报告文件。
     如果用户提供旧评审报告或要求对比，须逐项标为“保留”“撤回”或“本次新增”；
     证据不足时标为“待确认”并说明缺少的证据，不得静默漏项。
   - **完整文件和模块**：先核对目标清单和变体，再逐文件检查功能路径、调用接口、
     资源清理和可变状态；完成初始覆盖后进行端到端集成追踪，逐项核实疑点及
     共享状态，最后通过校验门禁生成 Markdown 报告。报告写入评审开始时的工作
     目录；每项发现分别记录规则标签与规则依据。中断或续评时保留同一记录和
     报告路径，并如实标注未完成状态。
     完整文件清单始终只有一个目标；支撑文件只提供契约证据，不增加目标覆盖数。
     初审要求四类调用点发现工作都有证据；集成要求登记的调用点逐项闭环。
     共享状态闭环或整段源码标记“已检查”不能替代边界/输入检查。
     报告分别给出风险清单和已登记调用点的完成数，不把计数当作绝对无遗漏证明。

若关键上下文不可获取或评审证据尚未闭环，Skill 会说明具体限制，不把未完成
的检查描述为通过。各阶段的详细门禁、记录方式和输出约定见
[`SKILL.md`](SKILL.md) 及其中引用的 `references/` 文档。
调用点发现和证据字段见
[`references/input-boundary-review.md`](references/input-boundary-review.md)。
旧 v3 台账仍可读取和续评，但缺少调用点清单时须补审后才能通过完成门禁。
调用点现在绑定源码表达式及内容哈希，不接受“剩余操作”或整文件范围代替；
每个适用的边界、错误、清理及调用方场景分别处置。容量、扫描宽度和生产者
约束需要结构化证据，不能仅写“内部输入安全”。提供旧报告时逐项保留、合并、
撤回或排除，并解释严重性变化。候选提取是词法辅助，不是完整 C/C++ 分析器，
门禁通过也不等于证明绝对无遗漏。
